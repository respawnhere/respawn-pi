# Design standards

How RespawnPack builds interfaces people can use, trust, and reach. The through-line: **an interface is a promise — every control that lies about what it does, every state that gives no feedback, every barrier a keyboard or screen-reader user hits is that promise broken.** Like scale failures, these are cheap to prevent at write time and brutal to retrofit after a user — or a support ticket — finds them. A confirm-before-delete step or a labeled input costs a line at build time and a migration later.

`/loadout` design-models user-facing work at plan time; `/build` writes to this standard; `/review` runs it as the `design-reviewer` lens; `/ship` gates UI changes on the §5 passes and the WCAG baseline. It is the visual/interaction sibling of [`coding-standards.md`](coding-standards.md), [`performance-standards.md`](performance-standards.md), [`writing-standards.md`](writing-standards.md), and [`behavior-standards.md`](behavior-standards.md).

**This page is the index.** It carries Rule 0 and each section's load-bearing checks — enough for most reviews to run from this page alone. The full rule list for a section lives in its detail file under `design-standards/`, for when a diff needs the depth (every WCAG criterion, the full type and color systems). A finding cites the section, and for accessibility the WCAG success-criterion number: "§3 choice overload", "§4 SC 1.4.3".

## Rule 0 — Stakes calibration

Apply full rigor to what a user directly operates — forms, destructive actions, navigation, anything above the fold — and to anything irreversible or high-stakes (a payment, a deletion, a legal or medical submission). A one-off internal screen or a marketing-page nit is not the same review as a data-destruction confirm flow, and treating them alike either drowns the low-stakes work in ceremony or under-protects the high-stakes work. Calibrate, don't dilute: scale the *ceiling* to the stakes, but never lower the *floor* — the accessibility baseline (§4) holds on every surface, because "low-stakes" never means "excludes a class of users." When in doubt about a surface's stakes, ask what the worst outcome of a mistake on it is; that answer sets the rigor.

## §1 — Interaction craft

The element is honest, the state is legible, the form forgives, the destructive action is survivable, the user's place outlives a refresh. The high-frequency checks: **semantic elements over `<div onClick>`** (native controls come with keyboard, focus, and role for free); **a visible focus indicator** never stripped without a `:focus-visible` replacement; **labeled, inline-validated forms** that parse forgiving input; **confirm-or-undo on every destructive action** — Undo for the routine (the stronger tool), confirmations that name the object and consequence, deliberate friction for the irreversible; **feedback inside the response window** (spinner past ~1s, cancelable past ~2s, progress + cancel past ~10s); **navigation state in the URL** so refresh and Back don't lose it; **specific action labels** ("Delete 3 files", never "Submit" or ALL CAPS); **state visible across interruptions** — what changed while the user was away is shown, and mode never switches silently. Semantic structure is an affordance for machine readers too, not only humans. → [`design-standards/01-interaction-craft.md`](design-standards/01-interaction-craft.md)

## §2 — Visual system

The systematic layer: could someone rebuild this screen from the tokens alone? The high-frequency checks: **tokens are the source of truth** — no hardcoded color/spacing/type/shadow literals bypassing them; **contrast is computed from the real values**, not eyeballed (→ §4); **a deliberate type scale** (px/rem, ~3–4 levels, weight before size) and **spacing scale** (grouping unambiguous — between-group gaps larger than within-group); **emphasize by de-emphasizing** secondary elements rather than shouting the primary; **dark mode is its own token set**, not a color inversion, with a counterpart for every component; **elevation as tokens** — shadow depth mapped to meaning (button / dropdown / modal), not eyeballed; **motion runs on `transform`/`opacity`** (never layout properties) and honors `prefers-reduced-motion`. Consistency is the default; per-user adaptation is earned and comes with a filter-bubble guardrail. → [`design-standards/02-visual-system.md`](design-standards/02-visual-system.md)

## §3 — Psychology of use

How the interface meets the mind using it. The high-frequency checks: **choice overload** — many undifferentiated options with no default or recommended path; **proximity / common region** — related controls grouped, unrelated ones separated, no ambiguous boundaries; **progressive disclosure** of advanced controls (optimize for less thinking, not fewer clicks); **recognition over recall** with sensible defaults, but never a defaulted sensitive field; **missing feedback is a trap** that produces double-submits; **deliberate friction before high-stakes irreversible actions**; **no dark patterns** (no pre-ticked consent, no buried opt-out); **slip-vs-mistake diagnosis** before prescribing a countermeasure (the cures are opposites); and when the surface embeds AI, **keep the user capable** rather than de-skilled. → [`design-standards/03-psychology-of-use.md`](design-standards/03-psychology-of-use.md)

## §4 — Accessibility baseline (WCAG 2.2 A / AA)

The floor, at full rigor on every surface regardless of Rule 0 stakes. The high-frequency checks, cite the SC by number: **contrast** — text ≥ 4.5:1; large text (≥24px, or ≥18.66px bold) and UI boundaries ≥ 3:1 (SC 1.4.3, 1.4.11); **never color alone** (SC 1.4.1); **keyboard-operable, focus never stuck** — a modal contains focus while open and returns it on close — **focus visible** (SC 2.1.1, 2.1.2, 2.4.7); **accessible names** on icon-only controls and **role-matched alt** on images, empty for decorative (SC 4.1.2, 1.1.1); **pointer targets ≥ 24×24 CSS px** (SC 2.5.8); **errors in text on the field, stating the fix when known** (SC 3.3.1, 3.3.3); **no forced re-entry** of data already given (SC 3.3.7); **auth without a memory or puzzle test** as the only path (SC 3.3.8); **a safety net on legal/financial/data-deleting actions** (SC 3.3.4); **status announced via live region** without stealing focus (SC 4.1.3); **structure in real markup** (SC 1.3.1). → [`design-standards/04-accessibility.md`](design-standards/04-accessibility.md)

## §5 — Validation probes

Prove §1–§4 by driving the interface, not reading the markup. The passes: **keyboard-only** (Tab through it — reachable, ordered, visible focus, no trap); **narrow-viewport** (320 CSS px — single column, nothing clipped); **reduced-motion** (`prefers-reduced-motion` set — non-essential motion gone); **contrast computed** from the real tokens, dark mode included; **semantics / screen-reader** (names, alts, live regions, real structure); **destructive & high-stakes trace** (confirm-or-undo, friction + safety net, state survives refresh); **state honesty** (feedback in-window, cancelable, errors in text). State which probes you ran versus inferred. → [`design-standards/05-validation.md`](design-standards/05-validation.md)

## The one-line test

Before a UI change ships, **drive it with the keyboard only, at 320px wide, with motion off, and compute the contrast from the real tokens.** If any one of those four breaks the interface for a class of users, it isn't done — no matter how good it looks at full width with a mouse.
