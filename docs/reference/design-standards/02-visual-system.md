# §2 · Visual system

Detail for §2 of [`design-standards.md`](../design-standards.md). The systematic layer beneath every screen: tokens, type, spacing, color, contrast, elevation, dark mode, and motion. The test running through all of it — **could someone rebuild this screen from the tokens alone, or is the design smuggled into hardcoded literals?** Calibrate depth to Rule 0.

**1. Tokens are the single source of truth.** Color, spacing, radius, type, shadow, and motion durations live as named tokens; components consume the tokens and never raw literals. A hardcoded `#3B82F6`, a stray `13px` margin, or a one-off `box-shadow` is drift — it dodges the system, can't be themed, and won't move when the token does. Tokens are also what make cross-platform and dark-mode consistency mechanical instead of manual. If a value belongs to the design system, it does not belong inline in a component.

**2. Build a deliberate type scale.** Hand-pick a constrained scale in px or rem — never `em`, which compounds fractional sizes in nested elements and breaks the scale. Body around 16px; cap the hierarchy at three or four levels. Establish that hierarchy with *weight* before reaching for size (bold reads as important without ballooning the layout), and skip a weight between body and heading for clean contrast. At the extremes: no weights below 400 for small UI text, and lighten large display headings rather than letting them sit heavy. Set line-height inverse to size (body ~1.5–1.6, large headings ~1.15–1.25) and proportional to measure; keep the measure ~45–75 characters. Two families at most, paired as opposites (a serif with a sans), never two near-identical faces.

**3. Build a spacing scale, and make grouping unambiguous.** Derive spacing from a base unit (4- or 8-based); keep no two steps closer than ~25% so choices are unforced. The load-bearing rule: the gap *between* groups must be visibly larger than the gap *within* a group — a label hugs its input, and the space below the input is larger — or elements read as unrelated and users make grouping errors. Put more space above a heading than below it so it binds to the section it introduces. Prefer whitespace and subtle tints to separate regions before you reach for borders, which sit in the foreground and add noise. When unsure, start with too much space and remove it.

**4. Emphasize by de-emphasizing.** Make the most important element dominant, but do it by turning *secondary* elements down — lower their contrast, mute their color, shrink them — rather than turning the primary one up until it shouts. Use the minimum emphasis that reads. Isolate the single primary action so it differs from its neighbors (the one thing that looks different is the thing remembered). Group related controls by proximity and shared region before adding boxes or rules.

**5. Compose color as a system, not a swatch pile.** Start from one primary hue chosen for the mood it sets, assign strict roles (primary / secondary / a single accent), and hold a rough 60/30/10 proportion. Generate variety as tints, shades, and tones of the base hues rather than adding new hues; anchor the whole thing with true neutrals (black, white, grey are not hues). Own one brand color and apply it consistently enough that the color alone signals you. Treat any hue's *meaning* as a plan-time hypothesis — validated against the actual audience in `/loadout`, not citable against a diff — because no color meaning is universal (red is luck in one place, mourning in another).

**6. Legibility is value contrast, and it is computed, not eyeballed.** What makes text readable is the lightness difference between it and its background, not the difference in hue — two colors close in value are hard to read even when the hues clash. Run every text-on-color and UI-boundary pairing through an actual contrast computation against the token values (→ §4 SC 1.4.3, 1.4.11), not a glance. Avoid placing two saturated complements edge to edge (the border visibly vibrates), and reserve full saturation for focal points. Never let color be the only signal (→ §4 SC 1.4.1); lean on the hardwired associations for status — red for error/stop, green for go/success, yellow-on-black for caution.

**7. Dark mode is its own token set, not an inversion.** Most smartphone users run dark mode where it's offered — it's a baseline, not a nicety. Define separate tokens for surface color, elevation, and text hierarchy in dark: shadows read differently on dark backgrounds (elevation often shifts to lighter surfaces, not deeper shadows), and a naive color-inversion fails contrast and creates OLED noise. Every component with a light treatment has a dark counterpart, and both are contrast-checked independently.

**8. Motion runs on the compositor and is always optional.** Animate `transform` and `opacity` — properties the browser can composite — never layout-triggering properties like `width`, `height`, `top`, or `left`, which force reflow and jank. Every non-essential animation honors `prefers-reduced-motion` as its default implementation (→ §4 SC 2.3.3), and motion earns its place by communicating status (a progress indicator that accelerates as it nears done) rather than decorating. Auto-playing, blinking, or scrolling content that runs past 5 seconds needs a pause/stop/hide control (→ §4 SC 2.2.2); nothing flashes more than three times a second (→ §4 SC 2.3.1).

**9. Encode depth as a consistent elevation system.** Shadows signal how far an element sits off the surface — a small shadow for a button, a medium one for a dropdown, a large diffuse one for a modal that needs to command attention. Define the elevation levels as tokens and apply them by meaning, not by eye, so "how raised is this?" always maps to the same answer.

**10. Treat density as a deliberate tradeoff.** Generous spacing is the default; tight packing is a conscious choice you make for a genuine reason (a dashboard or bento grid where users compare many values at a glance), not a way to fit more in. In a bento grid, vary card size to signal importance — uniform cards flatten hierarchy — and don't force flowing, step-based content into a grid. Expressive skins earn their place by carrying meaning: glass translucency only where the user needs the context behind it (an overlay revealing what it covers), neobrutalism or an off-white base as a deliberate, stated stance — never as a surface finish, and never at the cost of the contrast floor.

**11. Consistency is the default; adaptation is earned and guarded.** Strict internal consistency — the same tool in the same place behaving the same way — is what lets users transfer learning and what builds trust, and it's DRY: design an element once and reuse it through components and tokens. Real-time, per-user adaptation of layout or hierarchy is permitted only where it *demonstrably* helps, and never at the cost of the accessibility baseline or the predictability of a destructive action. When you do adapt, guard against the filter bubble: deliberately surface unfamiliar-but-relevant options in a low-cost zone so personalization doesn't quietly wall users off from features they haven't yet used (→ §3 rule 10).

**12. Catch the generic-AI look before it ships.** Indistinct gradients on every card, one border-radius-and-shadow combination applied to every surface, emoji standing in for icons, and placeholder-grade copy are the default-template tells — a screen built from framework defaults instead of the system this file describes. The fix is the evidence this file already demands: a real palette built from one chosen hue (rule 5), a deliberate type scale (rule 2), a spacing rhythm with an intentional base unit (rule 3). A screen with none of that evidence didn't skip a step of taste — it skipped the system.
