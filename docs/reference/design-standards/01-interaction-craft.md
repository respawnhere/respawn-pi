# §1 · Interaction craft

Detail for §1 of [`design-standards.md`](../design-standards.md). How controls behave under a real user's hands: **the element is honest about what it does, the state is always legible, the form forgives, the destructive action is survivable, and the user's place in the app outlives a refresh.** Calibrate depth to Rule 0 — a marketing button and a payment's confirm flow are not the same bar.

**1. Use the element that means the action.** `<button>` for an action, `<a href>` for navigation — never `<div onClick>`. A native control comes with keyboard operability, focus, and an assistive-tech role for free; a `div` reinvents all three and forgets at least one (usually the keyboard). If you must style a semantic element to look like something else, restyle it — don't swap the tag. This is the cheapest correctness win on the whole surface (→ §4 SC 4.1.2).

**2. Signify interactivity without requiring discovery.** A control must *look* operable before anyone hovers or taps it — on touch there is no cursor and no hover, so "no cursor = no hover = no clue." Every interesting visual feature (a raised edge, a shadow, an underline) reads as an invitation to act, so never dress a non-interactive thing to look pressable — that bait-and-switch spends the trust the rest of the surface earned. And map controls naturally to what they control: position mirrors the target, motion direction matches the effect (up/right reads as more/next) — a control whose direction fights its effect breaks the same contract.

**3. Never remove a focus outline without replacing it.** Focus is the keyboard user's cursor; `outline: none` with no `:focus-visible` replacement blinds them. Style focus deliberately as a first-class element — a brand-colored indicator at least 2px thick, carrying real contrast against both the focused and unfocused states — rather than leaving the browser default or stripping it (→ §4 SC 2.4.7, 2.4.13).

**4. Make controls pliant, and honest about their state.** A control visibly responds the instant it's engaged: a button depresses on press, a row highlights on selection. Commit on pointer-*up* over the control, so a user who starts a wrong click can abort by dragging off before releasing. Disabled controls are greyed in place — never hidden (users navigate by position; vanishing controls make the UI feel skittish) — and shed all hover/press response so their inertness is unambiguous. Selection and on/off state never ride on color alone (→ §4 SC 1.4.1).

**5. Every input carries a label and validates forgivingly.** A programmatic label plus any format hint ("MM/DD/YYYY") is present *before* the user guesses (→ §4 SC 3.3.2). Validate as focus leaves the field, inline, next to the control, in text — not in a post-submit modal and not by color alone (→ §4 SC 3.3.1). Parse what the user naturally types (spacing, capitalization, separators) instead of rejecting it; pre-fill sensible defaults from context or prior input — but never default a sensitive or high-stakes field (gender, payment amount, consent). When input merely looks wrong, flag it unobtrusively and let the user resolve it — never silently "fix" it; and don't halt the whole workflow on missing data where partial progress can be kept and nudged modelessly later.

**6. Acknowledge every action inside the perceptual window.** Match feedback to how long the work takes: under ~0.1s feels instant and needs nothing; 0.1–1s wants a subtle cue; 1–10s needs a spinner or progress bar; over 10s needs a progress meter with an estimate and a cancel control. Aim under 400ms where you can. Anything running past ~2s is cancelable with no side effects. Use optimistic UI and skeleton screens to buy perceived speed; build routine status into the interface (modeless) instead of interrupting with an "OK, saved" modal, and route non-focus-stealing updates through a live region (→ §4 SC 4.1.3). A click that gives no acknowledgment reads as broken and gets clicked again (→ §3).

**7. Give every destructive action a confirm-or-undo path.** Delete, cancel, revoke, overwrite — none of them may be a one-way trip with no net. For routine, reversible actions prefer *action + robust Undo* (a recycle bin, an undo stack — multi-level where possible) over a rote "Are you sure?" that users learn to dismiss blind. The two halves are not equals: undo is strictly the stronger tool, because a confirmation mostly stops slips, not mistakes — the user who misdiagnosed the situation confirms just as confidently — and only undo rescues them after the act (→ §3 rule 11). When you do confirm, make the actual object and consequence salient: name the thing being destroyed and what happens ("Delete the report 'Q3 forecast'? It cannot be recovered."), never a generic "Are you sure?" with the object nowhere in sight. For genuinely irreversible or high-stakes ones, add *deliberate friction* instead: a review step, a typed confirmation, a slowed second surface — interrupting the user's autopilot here reduces anxiety and error rather than adding annoyance (→ §3, Rule 0, §4 SC 3.3.4).

**8. Navigation state must survive a refresh and the Back button.** Active filters, the selected tab, the sort order, the page number, an open detail panel — reflect them in the URL (or otherwise restorable state). A user who refreshes, deep-links, or hits Back and loses their place has hit a broken contract. Client-side routing that only lives in memory is the usual culprit.

**9. Reuse conventions; they carry the user's prior knowledge.** People spend almost all their time in *other* products and arrive with those mental models (Jakob's Law) — logo top-left, a magnifier for search, a cart for checkout, standard toggles. Reach for the established pattern unless a new idiom is *measurably* better for your actual users, not just novel. Speak the user's model, never the implementation's — no database jargon, raw enum names, internal state codes, or naked error numbers surfacing in the interface. When consistency and clarity conflict, choose clarity.

**10. Label the specific effect; never shout.** Button and link text is a concrete verb naming what happens — "Send", "Delete 3 files", "Set up billing" — not "Submit" / "OK" / "Done". Link text stands on its own out of context (→ §4 SC 2.4.4) and matches the title of where it leads. Never ALL CAPS: readers recognize words by shape, and capitalizing every letter erases the shape and slows reading.

**11. Prevent the error before you write the message for it.** The best error message is the one the design made impossible — bounded controls (dropdowns, steppers, sliders) over free text for any value with a valid range, and disabling an invalid path instead of rejecting it after the fact. When an error is genuinely possible, the message is polite, plain, and specific, states how to fix it, and where it can, offers a control that applies the fix — never computerese, never a tone that blames the user for the system's rigidity (→ §4 SC 3.3.1, 3.3.3).

**12. Semantic structure is an affordance for machines, too.** In 2026 an AI agent often reads, summarizes, or acts on your interface before a human ever sees it. Real semantic HTML, a true heading hierarchy, and consistent labeling are the affordances that let a machine parse the surface correctly — and they are the *same* markup that serves a screen reader (→ §4 SC 1.3.1), so the work pays double. The checkable bar beyond §4: interactive elements and landmarks expose a stable semantic hook — a real role plus a durable accessible name that survive rebuilds and restyles — so an agent can re-locate and re-target them across sessions; a control findable only by pixel position or a generated class name fails it. Sound and motion are legitimate signifiers of state and interactivity in their own right — a click, a settle, a reactive weight — provided each is paired with a visible equivalent and honors reduced-motion (→ §2, §4 SC 2.3.3).

**13. State changes stay visible across interruptions — and are never made silently.** Users get pulled away mid-task; design for the return. On resume, show what changed while they were gone — a visible cue on anything that moved, arrived, or completed — instead of assuming they remember where things stood; an interface that looks identical after a background change invites acting on a state that no longer exists. The same contract binds the system's own transitions: never switch mode or state silently across an interruption or an automated handoff — an autopilot-style silent fallback leaves the user confidently operating a mode that is no longer running. After any automated transition, announce the new mode where the user is looking, not in a status corner they've learned to ignore, and route the announcement through a live region so it lands without stealing focus (→ §3 rule 11, §4 SC 4.1.3).
