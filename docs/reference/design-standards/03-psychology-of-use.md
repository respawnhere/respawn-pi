# §3 · Psychology of use

Detail for §3 of [`design-standards.md`](../design-standards.md). How the interface meets the mind using it: the load it imposes, the choices it forces, the feedback it withholds, and the traps — old (choice overload, missing acknowledgment) and new (dark patterns, de-skilling, the filter bubble). These are **the failures a static read of the markup misses and a real user hits on the first task.**

**1. Minimize the choices presented at once.** Decision time rises with the number and complexity of options (Hick's Law), so a screen of many similar, undifferentiated choices with no default and no recommended path stalls the user. Provide a sensible default, or make one path visually dominant and demote the rest; keep simultaneous choices to roughly three or four and reveal the long tail progressively. Design for *satisficing* — users take the first option that plainly works, they don't evaluate them all — so the job is to make the good-enough choice obvious, not to lay out every possibility with equal weight.

**2. Group related things; separate unrelated ones.** Controls that belong together are bound by proximity and a shared region; controls that don't are pushed apart. Ambiguous grouping — equal gaps within a set and between sets, or a boundary that straddles two unrelated groups — makes relationships unreadable and causes real errors (the user acts on the wrong control because it looked attached to the wrong label). This is the common-region and proximity lever from §2 applied as a usability check, not a decoration.

**3. Disclose progressively.** Show what the current task needs and defer the advanced or infrequent behind a "More" toggle, an accordion, or a secondary surface. Reducing visible complexity at first contact *increases* feature discovery over time, counterintuitive as that sounds — a wall of every option teaches users to ignore the whole region. Optimize for less *thinking*, not fewer clicks: users happily click several times when each step is small and unambiguous, and it's ambiguity, not click-count, that costs you. And if a surface needs instructional copy to be operable, treat that as the finding — users read instructions only after they've already failed; make the interaction self-explanatory and cut the instructions to the minimum.

**4. Favor recognition over recall.** Put the knowledge the user needs in the world, on the screen, rather than in their head — never make them memorize a value on one screen to retype on the next. Show a worked example or use a structured input where a specific format is required; let users pick from visible options instead of recalling a command. Carry sensible defaults from context and prior input — but never pre-fill a sensitive or high-stakes field, where a wrong, hard-to-notice default is worse than a blank.

**5. Chunk dense content; sequence long tasks.** Break walls of information into visually distinct groups of roughly four (±1) items — short-term memory holds about that much at once, which is why a bare 10-digit string is unreadable and a grouped phone number is easy. Split a long or complex task into a wizard of one-decision-at-a-time steps, and always show the user where they are in the sequence.

**6. Withheld feedback is itself a trap.** An action that produces no acknowledgment inside the response window (§1, rule 6) doesn't read as "working" — it reads as broken, and the user re-triggers it, producing the double-submit, the duplicate charge, the doubled message. Perceived responsiveness *is* perceived competence: instant, graceful acknowledgment of an input is read as system trustworthiness. The inverse also holds — an operation that finishes implausibly fast (a security scan that returns in 50ms) can read as *untrustworthy*, so a deliberate brief, animated pause sometimes raises confidence in the result.

**7. Add deliberate friction before high-stakes, irreversible actions.** The frictionless-by-default mandate is deliberately violated here: before a large payment, an account or data deletion, or a medical/legal/irreversible submission, *slow the flow on purpose* — a review step, a typed confirmation, a distinct second surface. Interrupting the user's autopilot at exactly these moments reduces anxiety and error and makes people feel *safer*, not more annoyed; the annoyance cost of a rote confirmation only shows up when you sprinkle it on routine, reversible actions (where §1's Undo is the right tool instead). Calibrate the friction to the stakes per Rule 0 (→ §1 rule 7, §4 SC 3.3.4).

**8. Refuse dark patterns.** No pre-ticked consent boxes, no defaults quietly set in the business's favor over the user's, no unsubscribe or account-deletion flow buried behind friction it doesn't need. Explain *why* data is collected, not just what; make leaving — deletion, export, opt-out — as easy as joining (aim for three clicks or fewer). Honest disclosure measurably improves long-term retention, so this is a retention strategy, not merely a compliance floor. The friction lever (rule 7) and this rule are opposites in intent: add friction to protect the *user* from a mistake, never to trap them into the *business's* preference.

**9. Design for the user's emotional state, not just the task state.** Interfaces meet people who are rushed, anxious, or already frustrated. Lower the temperature during high-stakes flows (payments, medical forms, legal submissions); rewrite raw technical errors into plain, reassuring language that says what to do next; and treat an empty state as a first-run onboarding opportunity — an illustration, a one-line orientation, and a single emphasized primary action ("Add your first contact") — rather than a dead-end "No items found." Voice stays stable; tone flexes with the moment (empathetic on error, celebratory on success).

**10. When the surface embeds AI or adapts per-user, keep the user capable — and unbubbled.** An assistant that does too much de-skills the person relying on it — a genuinely new trap with no analogue in the classic "easier is always better" canon. Calibrate how much the assistant does versus leaves to the user: rely on it *just enough, but not too much*, so the user stays competent rather than dependent and helpless when it's wrong or absent. Make what the assistant did visible and reviewable, keep an easy path for the user to take over or correct it, and don't let automation quietly remove the user's understanding of their own task. The same balance governs personalization: an interface that adapts only to observed behavior walls users off from what they haven't tried yet — the filter bubble — so deliberately surface unfamiliar-but-relevant options in a low-interaction-cost zone (→ §2 rule 11). This is the same balance-of-agency concern the Rule 0 stakes calibration turns on: the higher the stakes, the more the human stays in the loop.

**11. Diagnose slip versus mistake before prescribing — the cures are opposites.** Two different failures wear the same face in an error report. A *slip* is right intention, wrong execution: the adjacent button, the autopilot habit firing in the wrong context, the skipped step. Counter slips with constraints, spacing and visual differentiation of dangerous controls, undo, and confirmations that name the object (→ §1 rule 7). A *mistake* is wrong intention from a wrong mental model: the user did exactly what they meant to do, and what they meant was wrong. Confirmations are nearly useless against mistakes — the user confirms as confidently as they acted — so counter them with a clearer system image, visible state, and feedback rich enough for the model to self-correct. Classify an observed error before reaching for a fix: apart from undo — the recovery net that catches both classes after the act, which is why §1 rule 7 ranks it above confirmation — the countermeasures for one class do nothing for the other, and the reflexive "add a confirmation" treats every error as a slip.
